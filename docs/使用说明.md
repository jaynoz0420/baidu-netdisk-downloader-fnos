# 百度网盘下载器 · fnOS 应用

飞牛 fnOS 上的百度网盘下载工具。**1MB 分片 + 32 线程并发**，实测 **34~37 MB/s**，
解决官方 NAS 客户端下载被限速到几百 KB/s 的问题。

---

## 一、安装

### 方式 A：应用中心安装（推荐）

1. 打开 fnOS「应用中心」
2. 右上角「手动安装」→ 选择 `百度网盘下载器-fnOS-v1.0.0.fpk`
3. 安装完成后，桌面会出现「百度网盘下载器」图标，点击即可打开

### 方式 B：命令行安装

```bash
# 上传 fpk 到 NAS
scp 百度网盘下载器-fnOS-v1.0.0.fpk jaynoz@192.168.0.176:/tmp/

# SSH 登录后安装
ssh jaynoz@192.168.0.176
echo '<你的密码>' | sudo -S appcenter-cli install-fpk -v 1 /tmp/百度网盘下载器-fnOS-v1.0.0.fpk
echo '<你的密码>' | sudo -S appcenter-cli start baidu.nasdl
```

### 访问地址

安装并启动后，访问：

```
http://<NAS的IP>:18080
```

如果应用中心里点图标打不开，直接用上面的地址访问即可（端口 18080 是应用自身监听的，
不依赖 nginx 反代）。

## 二、登录

支持两种方式，任选其一。

### 扫码登录（推荐，最安全）

1. 打开应用页面，默认就是「扫码登录」标签
2. 用手机百度 App 扫描二维码
3. 手机上确认后，页面自动登录

二维码有效期 5 分钟，过期点「刷新二维码」重新获取。

### Cookie 登录

适合扫码不方便时使用。

1. 在 PC 上以**管理员身份**运行 `百度网盘-PC端cookie提取器.py`
2. 得到 `pc_cookie_str.txt`，内容形如：
   ```
   BDUSS=xxxxx; STOKEN=xxxxx
   ```
3. 切到「Cookie 登录」标签，粘贴进去，点登录

> Cookie 等同于账号密码，请勿外传。用完后可在百度网盘「账号安全」里
> 「退出所有设备」，让旧 cookie 失效。

## 三、使用

### 浏览与下载

1. 进「网盘文件」标签，点击文件夹名进入下一级
2. 点右上角「↑ 上级」返回上一层
3. 找到文件后点右侧「下载」按钮，任务自动开始
4. 切到「下载任务」标签查看进度、速度、暂停/继续/删除

下载的文件按网盘里的原目录结构，保存到设置的下载目录下。

### 选择下载目录（每次下载都弹窗）

**每次点击下载都会弹出目录选择框**，让你确认这次保存到哪。适用于所有下载方式：

- 单个文件「下载」
- 单个文件夹「下载」
- 批量勾选「下载选中」

弹窗的**默认目录是上次下载用过的目录**，所以连续下多个文件时不用每次都重新选。

弹窗里的操作：

- 点击文件夹**进入**下一级，**双击**也可以
- 点「↑ 上级」返回
- 也可以直接在下方输入框里**手打路径**，比如 `/vol1/1001/电影`
- 点「确定使用此目录」开始下载

**文件夹列表按修改时间倒序排列**（最近改过的在上），目录名后面显示修改时间，方便找最近用过的位置。

> 「设置」页里的默认下载目录旁边也有「浏览…」按钮，用同样的弹窗选。

如果还没下载过任何文件，弹窗默认打开「设置」里配置的默认下载目录。

### 文件保存位置规则

下载后文件放在哪，**单文件和文件夹的行为不同**：

| 下载方式 | 保存位置 | 示例 |
|---|---|---|
| **单个文件** | 直接放在你选的目录里 | `目标目录/xxx.mp4` |
| **单个文件夹** | 目标目录下建同名文件夹 | `目标目录/蒸蒸日上/xxx.mp4` |
| **批量（纯文件）** | 都放在你选的目录里 | `目标目录/a.mp4`、`b.mp4` |
| **批量（含文件夹）** | 每层文件夹各建同名目录 | `目标目录/蒸蒸日上/xxx.mp4` |

**关键点：不会重建网盘里的完整路径层级。**

举例：网盘里的文件在 `/我的资源/蒸蒸日上/某剧.mp4`

- 你选 `/vol1/电影` 下载**这个文件** → 得到 `/vol1/电影/某剧.mp4`
- 你选 `/vol1/电影` 下载**「蒸蒸日上」文件夹** → 得到 `/vol1/电影/蒸蒸日上/某剧.mp4`

不会出现 `/vol1/电影/我的资源/蒸蒸日上/某剧.mp4` 这种多余层级。

> v1.7.1 修复：此前单文件下载会把网盘路径也复制过来，多出「我的资源/蒸蒸日上」两层目录。

### 排序

文件列表默认按**修改时间倒序**排列（最新的在前），文件夹始终排在最前面。

右上角提供 4 种排序方式，点一下即时生效：

| 按钮 | 说明 |
|---|---|
| 修改时间 ↓（默认） | 最新修改的在前 |
| 修改时间 ↑ | 最早的在前 |
| 名称 A→Z | 中文/英文按字典序正序 |
| 名称 Z→A | 倒序 |

### 批量下载

1. 勾选左侧复选框选择多个文件或文件夹（可以混选）
2. 表头复选框可一键全选当前目录
3. 底部会出现蓝色操作栏，显示「已选 N 项」
4. 点「下载选中」，确认后自动开始

**文件夹会自动递归展开**：选中一个文件夹，会把它下面**所有层级**的文件都加入下载队列，
并在本地创建完全一致的目录结构。

例如网盘里的：
```
/剧集/某剧第一季/
├── 01.mkv
├── 02.mkv
└── 花絮/
    └── 幕后.mkv
```

勾选「某剧第一季」后，本地会得到：
```
<下载目录>/某剧第一季/
├── 01.mkv
├── 02.mkv
└── 花絮/
    └── 幕后.mkv
```

演示：选中一个 174 个文件的文件夹，一次性创建 174 个下载任务，目录结构完整还原。

### 文件属主（权限）

下载器以 root 身份运行，但**新建的目录和文件会自动继承目标目录的属主**，
不会留下一堆 `root:root` 的文件导致你在 fnOS 文件管理器里打不开、删不掉。

举例：默认下载目录 `/vol1/1001/Backup` 属于 `jaynoz:Users`，
那么下载器创建的所有内容都会是 `jaynoz:Users`：

```
/vol1/1001/Backup/生化危机爆发夜/                    jaynoz:Users
/vol1/1001/Backup/生化危机爆发夜/xxx.mkv               jaynoz:Users
```

具体做法是从下载路径**向上查找第一个非 root 的祖先目录**，取它的 uid/gid，
应用到所有新建的目录、`.part` 临时文件、断点续传的 `.meta.json` 和最终成品。
并发批量下载时也共用同一个属主值，避免多任务互相干扰。

> 如果你把下载目录指向了别的位置，属主会跟随那个目录的实际属主。

### 设置

「设置」标签里可以改：

| 项目 | 说明 |
|---|---|
| 默认下载目录 | 默认 `/vol1/1001/Backup`，可改成任意 NAS 路径 |
| 单任务并发 | 默认 **64**。单个任务最多开几条连接 |
| 总连接预算 | 默认 **64**。**所有任务合计**的连接上限 |
| 同时下载任务数 | 默认 **1**，最高 **3**。其余任务排队 |
| 总下载限速 | 默认 **0（不限速）**。所有任务合计的速度上限 |

### 总下载限速

下载默认跑**最大速率**（约 35～38 MB/s）。如果下载时影响其他设备播放视频，
可以在「设置」里给一个总限速：

| 项目 | 说明 |
|---|---|
| 总下载限速 | 单位 MB/s，**所有任务合计**的上限。`0` = 不限速 |

**实测**：

| 配置 | 实测速度 |
|---|---|
| 不限速（默认） | **38.36 MB/s** |
| 限速 10 MB/s | **9.41 MB/s** |

调速建议：

| 场景 | 建议值 |
|---|---|
| 不看视频 / 夜间下载 | `0`（不限速） |
| 边下边看，想兼顾 | `15～20` |
| 播放优先，稳定流畅 | `8～12` |
| 播放仍卡顿 | `5` |

> 限速**立即生效**，不需要重启任务。

### 任务列表排序

任务列表按**状态优先级**自动排列，从上到下依次是：

| 顺序 | 状态 | 组内排序 |
|---|---|---|
| 1 | ▶ 下载中 | 先开始的在前 |
| 2 | ⏳ 排队中 | **按即将下载的顺序**，越靠上越先下 |
| 3 | ⏸ 已暂停 | 最近添加的在前 |
| 4 | ✗ 出错 / ✓ 已完成 | 最近添加的在前 |

也就是说：**当前在下载的任务永远在最上面**，下面是排队队列，
第一行排队的就是下一个要下载的。它们会随着下载推进自动往上移动。

举例：

```
1. ▶ 下载中   S01E04  6.7%     ← 正在下
2. ⏳ 排队     S01E17          ← 下一个就是它
3. ⏳ 排队     S01E03
4. ⏳ 排队     S01E08
5. ⏳ 排队     S01E18
6. ⏳ 排队     S01E14
```

S01E04 下完后，S01E17 会自动变成「下载中」升到第 1 位，其余依次上移。

### 任务批量操作

「下载任务」页顶部有操作栏，支持：

| 按钮 | 作用 |
|---|---|
| 全部暂停 | 暂停所有运行中/排队中的任务 |
| 全部开始 | 恢复所有已暂停的任务 |
| 暂停选中 | 只暂停勾选的任务 |
| 开始选中 | 只恢复勾选的任务 |
| 清除已完成 | 清除已完成/出错的任务（不删文件） |
| 删除选中 | 删除勾选的任务 |

勾选方式：每条任务左侧的复选框，或表头「全选」一次勾上全部。

批量操作都是**非阻塞**的，点完立即返回，后台完成收尾：

| 操作 | 6 个任务实测耗时 |
|---|---|
| 批量删除 | **0.13 秒** |
| 暂停单个 | **0.02 秒** |
| 恢复单个 | **0.00 秒** |

删除后线程会自动回收，不会残留在后台。

### 总速度面板

任务页顶部实时显示：

- **总速度** — 所有运行中任务的合计速度（大号蓝色数字）
- 运行中 / 排队 / 已完成 / 已暂停 各状态的个数
- **已下载** — 所有任务的累计下载量
- 右侧**速度曲线** — 最近 30 次采样的走势

没有任务在跑时，数字变灰显示 `0.00`。

### 并发调度（重要）

百度 CDN 对**同一账号的总带宽**有限制。实测（空载、纯网络读、同一账号）：

| 连接数 | 实际速度 |
|---|---|
| 16 | 9.2 MB/s |
| 32 | 17.7 MB/s |
| **64** | **22.8 MB/s** ← 最优 |
| 96 | 19.7 MB/s ← 反而下降 |

所以**单任务 64 连接是最快的**。如果同时开 3 个任务、每个都 64 连接，
总并发会超出限制，结果每个都被压到很慢。

下载器的处理方式：

**1. 队列调度**：只让「同时下载任务数」个任务真正跑，其余显示「排队中」。

**2. 预算均分**：总连接预算按运行中任务数分配。

**实测对比**（同一批 5GB 文件）：

| 配置 | 单任务速度 | 合计 |
|---|---|---|
| 旧版：3 任务各 10 连接 | 8 MB/s | 25 MB/s |
| **新版：1 任务 64 连接** | **37 MB/s** | **37 MB/s** |

**建议**：保持默认（同时 1 个、预算 64）。单任务能跑满带宽，
而且不会因为并发过高被百度限速。多个任务会自动排队，一个接一个下完。

> 如果想让几个任务「同时有点进度」，可以把同时任务数调到 2～3，
> 但每个任务会分到更少连接，单任务速度下降、总速度基本不变。

## 四、为什么快 / 技术原理

官方 NAS 客户端（`clienttype=29`）走 P2P 通道时，服务端 CDN 对单条连接做了
约 100~300 KB/s 的流量整形。实测发现 CDN 的风控规则是按 HTTP Range 大小判断：

| Range 大小 | 结果 |
|---|---|
| ≤ 1 MB | 200 OK，正常返回 |
| ≥ 10 MB | 403 Forbidden |

大 Range 被拒后，官方客户端只能退回小分片串行拉取，每条连接又被限速，
所以 NAS 端始终只有几百 KB/s。而 **1MB 分片 + 32 并发**能让带宽线性叠加：

```
1 线程  →  0.97 MB/s
4 线程  →  4.88 MB/s
8 线程  →  8.39 MB/s
16 线程 → 17.48 MB/s
32 线程 → 34.38 MB/s
```

实测 5.17 GB 文件 153 秒下完，平均 34.58 MB/s，与 PC 端速度相当。

**支持断点续传**：中断后重跑会读取 `.meta.json` 里已完成的分片记录，只补缺失部分。

## 五、常见问题

**Q：应用中心点图标打不开页面？**

用 `http://<NAS_IP>:18080` 直接访问。应用启动时会自动把真实地址写进
`ui/config`，但如果 fnOS 缓存了旧配置，直接输地址最稳。

**Q：端口 18080 被占用？**

编辑 `/var/apps/baidu.nasdl/cmd/config`，把 `APP_PORT=18080` 改成别的，
然后 `appcenter-cli stop baidu.nasdl && appcenter-cli start baidu.nasdl`。

**Q：接口时好时坏、任务列表对不上、删除报 404？**

这是**多个进程同时运行**导致的。从 v1.7.0 起采用**接管机制**：

- 检测到旧实例还活着 → 先 `SIGTERM` 让它优雅退出
- 5 秒内没退出就 `SIGKILL` 强杀
- 由新进程接管端口与 socket，最终**只保留一个完整实例**

日志会明确记录：

```
检测到旧实例 pid=1181376, 接管中…
旧实例已退出, 由本进程接管
监听 Unix socket: /var/run/baidu.nasdl.sock
监听 TCP: 0.0.0.0:18080
```

下载任务支持断点续传，接管不会丢失进度。

如果仍有异常，手动清理一次即可：

```bash
pkill -9 -f baidu.nasdl/server.py
rm -f /var/run/baidu.nasdl.sock /vol1/@appdata/baidu.nasdl/server.lock
appcenter-cli start baidu.nasdl
```

**Q：应用中心点「启用」报「本地应用启动失败」（错误码 10330）？**

v1.7.0 已修复。原因有两层：

1. **旧逻辑缺陷**：v1.6.1 的单实例锁发现存活实例就静默退出，而 appcenter
   把「进程启动后立刻消失」判定为启动失败 —— 即使旧进程其实还在正常服务。
2. **就绪判定太弱**：`cmd/service` 只检查 socket 文件是否存在，服务没真正
   应答就报成功，后续操作会失败。

现在的做法：

| 环节 | 修复 |
|---|---|
| 单实例 | 改为**接管**：终止旧实例后自己完整启动，appcenter 看到的是一次成功的启动 |
| 就绪探测 | socket 存在**且** `/api/ping` 返回 `"ok"` 才算就绪，最多等 30 秒 |
| 失败反馈 | 未就绪时返回失败并打印日志尾部，不再假装成功 |

实测连续执行「停止 → 启动 → 停止 → 启动」四轮，全部返回 `running`，
无 10330 错误。

**Q：删除任务要等很久？**

v1.6.1 起改为非阻塞：暂停/删除只置停止标记，flush 缓冲和删文件都在后台线程完成，
接口立即返回。实测删 6 个任务从 26 秒降到 **0.13 秒**。

**Q：下载速度掉到几百 KB/s？**

- 检查「设置」里的并发数是否为 32
- 确认 NAS 没有别的程序占满带宽
- 下载到 100% 前的最后几个分片会慢一些，属正常

**Q：Cookie 过期了？**

重新跑一次 `百度网盘-PC端cookie提取器.py`（PC 端需保持登录），
或用扫码登录（永久有效，无需担心过期）。

**Q：下载的文件放哪了？**

默认 `/vol1/1001/Backup/<网盘原目录结构>/`。「下载任务」里每个任务都显示了完整路径。

**Q：如何卸载？**

应用中心里卸载即可。已下载的文件会保留。命令行：
```bash
sudo appcenter-cli stop baidu.nasdl
sudo appcenter-cli uninstall baidu.nasdl
```

```json
{
  "action": "pause",          // pause | resume | delete
  "ids": ["id1", "id2"],      // 可选，不传则作用于所有符合条件的任务
  "remove_file": false        // 仅 delete 用，是否同时删本地文件
}
```

返回：
```json
{"ok": true, "action": "pause", "matched": 3, "affected": 3, "errors": []}
```

### 批量下载接口示例

```json
POST /api/download/batch
{
  "items": [
    {"fs_id": "123", "name": "a.mkv", "path": "/dir/a.mkv", "size": 1024, "isdir": false},
    {"fs_id": "456", "name": "子目录", "path": "/dir/子目录", "isdir": true}
  ],
  "out_dir": "/vol1/1001/电影",
  "conns": 32
}
```

`out_dir` 可选，不传则用配置里的默认下载目录。

返回：
```json
{
  "ok": true,
  "selected": 2,
  "expanded": 15,
  "deduped": 0,
  "created": 15,
  "skipped": [],
  "failed": []
}
```

`expanded` 是展开后的文件总数（文件夹已递归），`deduped` 是重复 fs_id 被去掉的数量。

### 单个下载接口

```json
POST /api/download
{
  "fs_id": "123",
  "name": "a.mkv",
  "path": "/dir/a.mkv",
  "size": 1024,
  "out_dir": "/vol1/1001/电影",
  "conns": 32
}
```

同样支持 `out_dir`，不传则用默认目录。
